2) “Что осталось” — приоритетный список

P0 (блокеры до запуска с реальными деньгами)

Цена: UI vs checkout расходятся
Факт: в product page цена может вычисляться из price_cents, а в создании заказа берётся ecom_products.price (route.ts (line 445)).
Что сделать: либо (а) в orders-create брать price_cents (и фоллбек на price*100), либо (б) гарантированно синхронизировать price при обновлении price_cents в feed.
Stripe status "processing" несовместим с enum payment_status
Факт: mapPaymentStatus возвращает "processing" (utils.ts (line 115)), а в схеме payment_status enum не содержит processing → запись в payments может падать, триггеры не обновят orders.status на paid.
Что сделать: маппить processing → pending/requires_action (или расширять enum, но это тяжелее).
Customer RMA endpoint не соответствует схеме
Факт: endpoint пытается писать user_id/metadata/note и status:"pending" (route.ts (line 71)), а в схеме rma_requests нет уникальности по order_id и статусы другие (requested/approved/...).
Что сделать: привести endpoint к реальным колонкам (notes, статус requested), и/или добавить unique constraint по order_id, если бизнес‑правило “1 RMA на заказ”.
Безопасность cron‑секрета
Факт: client-side код шлёт x-cron-secret из NEXT_PUBLIC_CRON_SECRET (shipments-client.tsx (line 197)). Если это задано в проде — секрет по сути публичный.
Что сделать: убрать заголовок совсем (админ и так авторизован cookie/JWT), оставить CRON_SECRET только server-side.
PO creation надёжность
Факт: PO создаётся из webhook через void createPurchaseOrderForPaidOrder(...) (не awaited) — в serverless это может быть недетерминированно.
Что сделать: либо await (и выдержать таймаут), либо писать “job” в БД и отдельным cron/worker добивать (лучше).
Idempotency/дедуп purchase_order_items
Факт: в схеме нет unique constraint на purchase_order_items (например (purchase_order_id, order_item_id)), сейчас возможны дубли при ретраях/гонках.
Что сделать: добавить unique + адаптировать insert на upsert/ignore duplicates.

4) Проверки/тесты (чеклист сценариев + что добавить первым делом)

Чеклист сценариев (реальные, руками прогнать в staging)

Happy path
SKU в наличии → orders-create → payments/create → webhook payment_intent.succeeded → orders.status становится paid (через payments‑триггеры) → создан purchase_orders + purchase_order_items → создан shipments → email_outbox queued → process → письмо ушло.
OOS между cart и оплатой
После добавления в cart выключить ecom_products.is_available=false/stock_quantity=0 → убедиться, что перед оплатой ты либо блокируешь payments/create, либо после оплаты автоматически ставишь кейс в manual review/refund.
price changed
Обновить price_cents и не трогать price → проверить: цена на карточке ≠ цена в заказе (сейчас это вероятно) → это P0.
missing supplier_skus
Оплатить SKU без маппинга → ожидание: purchase_orders.status='failed', понятный алерт/лог + понятная процедура “refund или ручной supplier mapping и повтор PO”.
duplicate webhook
Прислать один и тот же Stripe event дважды параллельно → ожидание: второй не ломает систему, не создаёт дублей PO/items, не шлёт повторные нотификации.
shipment exception/returned
Поставить shipment exception/returned → ожидание: PO статус обновился (failed/cancelled), клиент получил письмо/видит статус, есть workflow для refund/RMA.
refund/RMA
Refund: из paid сделать refund → refund_order_apply должен перевести orders.status в refunded, и деньги/статусы не должны зависнуть.
RMA: клиент создаёт request → запись создаётся 1 раз на order (или явно разрешены множественные), статусы валидные (requested/...), админ может обновить.
Какие тесты/фикстуры добавить первыми (самый ROI)

Тест на “валидность статусов” для Stripe маппинга: mapPaymentStatus никогда не возвращает значение вне enum payment_status (сейчас нарушается на processing).
Тест на “price source of truth”: order creation использует тот же источник, что и UI (если UI показывает price_cents, то и заказ должен фиксировать это).
Тест на идемпотентность PO items: повторный вызов PO creation не создаёт дублей (после добавления unique constraint).
Тест на RMA endpoint соответствие схеме: создание RMA не делает onConflict по полю без unique и не пишет несуществующие колонки.
Тест на email_outbox “no duplicates”: два параллельных process (или два последовательных) не отправляют одно письмо дважды (после внедрения claim/lock).
